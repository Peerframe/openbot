# Research: Python control-plane authenticated read slice

- Status: Implemented and locally accepted for S2a-1; hosted Linux CI pending.
- Date: 2026-09-23
- Owner: OpenBot maintainers
- Acceptance journey: an existing Owner session reads matching valid Bot/channel records through a
  separate Python API against the same synthetic PostgreSQL fixture; revoked/expired sessions fail.
- Security boundary: reference read-only API, no task dispatch, no model credentials, no migrations,
  no authentication issuance or writes. The existing Server remains the only writer in this slice.

## Reuse decision

Use OpenAPI and released ASGI/Pydantic/PostgreSQL components. The OpenBot-specific adapter maps
existing business rows and validates existing session digests; no authentication protocol, SQL
migration engine, password system or second source of task truth is added. Native SQL through
Psycopg preserves reviewed table semantics without importing another ORM's schema lifecycle.

The first slice exposes health, auth/session, bots and channels only. Existing TS session issuance
continues; Python receives only the request cookie and hashes it for a parameterized lookup.
Use the existing secure/plain cookie names according to fixed configuration. Read authorization
and projection within a bounded read-only transaction and recheck revocation before returning.
Malformed state or storage failure is unavailable, not an anonymous success or a fabricated list.
No secret configuration, password, token digest, or raw database exception reaches the response.
Disable interactive docs and expose only the selected OpenAPI schema. No production default changes.

The source lineage check has established incompatible feature/migration histories. Startup must
verify the selected target's exact SQL timestamp/hash history and refuse every other lineage; it
must not migrate or rewrite it. Cross-lineage transfer is a separate S7 deliverable. Real fixtures
must use the existing Node migrator to prepare an owned temporary PostgreSQL instance.

## Source incorporation

No external source copied or substantially adapted. Existing MIT OpenBot behavior is reimplemented
through released interfaces. License metadata for dependencies stays installed; note Psycopg's LGPL
terms in the package README. No library internals are vendored or patched.

## Verification plan

- Strict projection fixtures: Unicode, UTC timestamps, optional fields, appearance filtering and no
  private configuration leakage; OpenAPI schemas reflect actual response envelopes.
- HTTP boundary: missing/revoked/expired session, wrong cookie mode, different app instances,
  mutation rejection, fixed errors, no-store headers and credentialed CORS limited to configured origins.
- Actual paired Server/Python/PostgreSQL fixture: one TS-issued session, shared rows, response
  equality, subsequent revocation, rejected SQL write under the read-only connection, schema drift
  and startup failure. No private environment/model credentials or old user database.
- Required package checks plus npm run check. Linux qualification follows the accepted fixture pattern.

## Unresolved scope

Login/logout issuance is now implemented separately in [S2a-2](python-owner-auth.md). Business writes,
global snapshot revision/event contracts, scheduling, task ownership, client generation and production
selection remain later S2 slices. These four reads alone do not
make Python the primary backend. Do not claim complete client parity or cross-lineage migration.

## Local acceptance and intentional data boundary

The 198 package cases and nine owned PostgreSQL/HTTP cases pass for the combined S2a-1/2 slice.
DeepSeek contributed 128 independent projection cases; Codex reviewed them, added four strict
boolean-discriminator cases, and tested malformed stored status against real PostgreSQL. Illegal
Bot status returns 503 for the whole list rather than exposing the old unchecked value. Malformed
appearance is omitted instead of accepting JavaScript coercion. No stored row is rewritten.
Valid rows match the actual TS API; only membership order is normalized because its old contract
is unspecified. Local macOS execution plus a Linux PostgreSQL container is not hosted Linux Python
qualification. The two upstream client deprecation warnings are retained at reviewed pins.
