# 研究：有界的 Windows 安装进度检查

- 状态：接受实施，必须经过 Windows 原生验证
- 日期：2026-09-15
- 范围：仅修改安装验收夹具，不改变安装器、用户数据或安全策略。

完整来源和精确版本见[英文记录](windows-installer-progress.md)。已检查既有冷启动、回执清理复用记录，electron-builder 26.16.1 / `7d3b30f3b15950d19f7c5ff882cf2d161cd3ba2c`、NSIS 3.0.4.1 模板及测试、MIT/NSIS 许可、当前上游问题和微软 Process API 文档。未找到与本次 Windows 原生故障一致的已确认上游修复；Wine 的 PowerShell 提案不适用。

PR #71 最后一次成功检查中，安装前置检查结束到首次 Electron 启动经过 102.26 秒，包含安装和 ASAR 校验，不能当作纯安装耗时。最终 PR 是下载 HTTP 504；后来的 main 与 PR #72 则被无条件的 120 秒安装上限中止。旧日志尚不能区分解压慢和进程检查停滞。

复用 PowerShell/.NET 的持有进程对象、Stopwatch 和有界 WaitForExit，记录测试安装目录内的文件数、字节数与持有安装进程的 CPU 时间。文件增长或累计至少 250 毫秒的 CPU 工作延长 120 秒的停滞期限，同时保留独立的 300 秒总上限。仅记录耗时、数量和 CPU 时间，不收集凭据、命令行或用户进程。进程存活或持续占用 CPU 本身不能通过验收。

超时后通过持有的进程对象终止安装器进程树，并有界等待，再执行卸载和夹具清理。等待根进程退出不等于证明所有脱离进程都已退出，不扩大原有保证。安装退出码、已安装 ASAR 一致性、原生启动、十次独立冷启动与卸载要求全部保留。

不采用简单增加固定超时、忽略失败、排除安全扫描或复制安装器模板。没有新增依赖或复制上游源码。CI 增加真实进程夹具，覆盖持续进展、停滞和总时限；实际安装日志必须证明旧时限之后是否仍在解压。如果仍停滞，继续据证据修复对应环节，不能把等待更久当作根因修复。

## PR #96：识别目标目录写入之前的工作（2026-09-26）

[失败的 Windows 检查](https://github.com/Peerframe/openbot/actions/runs/36166820890/job/108176484131)
在 120 秒时尚无目标文件，但持有安装进程的 CPU 时间从第 75 秒的 0.86 秒增至终止时的
13.78 秒。前一次成功检查也在尚无目标文件时累计了 26.64 秒 CPU，最终安装耗时 117.34 秒。
旧监测器记录 CPU 却未将其计入停滞判断。

重新核对复用记录与固定版本 NSIS 模板后确认：归档先写入 `$PLUGINSDIR`，再解压到
`$PLUGINSDIR/7z-out`，最后才复制到目标目录。仅观察目标目录无法覆盖前面的工作。
这证明监测存在缺口，尚不能确定失败时具体由哪一步消耗 CPU。来源、精确提交和 GitHub
搜索记录见英文文档；没有证据支持替换或修改安装器。

沿用 `.NET TotalProcessorTime`，累计至少 250 毫秒 CPU 增量才更新活跃时间，避免每次微小唤醒
都被当作进展；读取失败不产生虚构进展。保留 120 秒停滞期限、300 秒总上限、退出码、ASAR
一致性、十次冷启动及卸载检查。不扫描共享临时目录或其他进程。

真实进程回归增加：只消耗 CPU 后完成、CPU 工作后停滞、无限 CPU 循环仍触发总上限。
保留文件增长、睡眠停滞、文件增长总时限与非零退出测试。实际 Windows 安装必须再次通过；
没有新增依赖、复制上游源码、修改产品行为或降低成功条件。

提交前，旧监测器在本机复现了 2.5 秒时已有 2.78 秒 CPU 工作却被判停滞的问题。
新版本的七项真实进程回归在 macOS PowerShell 7.5.2 与 Linux PowerShell 夹具中均通过，
CPU 单独活跃的用例在旧版本中失败。这证明共享监测逻辑与时限，不能替代 Windows 安装验收。
