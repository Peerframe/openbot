# 研究：有界的 Windows 安装进度检查

- 状态：接受实施，必须经过 Windows 原生验证
- 日期：2026-09-15
- 范围：仅修改安装验收夹具，不改变安装器、用户数据或安全策略。

完整来源和精确版本见[英文记录](windows-installer-progress.md)。已检查既有冷启动、回执清理复用记录，electron-builder 26.16.1 / `7d3b30f3b15950d19f7c5ff882cf2d161cd3ba2c`、NSIS 3.0.4.1 模板及测试、MIT/NSIS 许可、当前上游问题和微软 Process API 文档。未找到与本次 Windows 原生故障一致的已确认上游修复；Wine 的 PowerShell 提案不适用。

PR #71 最后一次成功检查中，安装前置检查结束到首次 Electron 启动经过 102.26 秒，包含安装和 ASAR 校验，不能当作纯安装耗时。最终 PR 是下载 HTTP 504；后来的 main 与 PR #72 则被无条件的 120 秒安装上限中止。旧日志尚不能区分解压慢和进程检查停滞。

复用 PowerShell/.NET 的持有进程对象、Stopwatch 和有界 WaitForExit，记录测试安装目录内的文件数与字节数。只有实际写入进展才延长 120 秒的停滞期限，同时保留独立的 300 秒总上限。仅记录耗时、数量和 CPU 时间，不收集凭据、命令行或用户进程。

超时后通过持有的进程对象终止安装器进程树，并有界等待，再执行卸载和夹具清理。等待根进程退出不等于证明所有脱离进程都已退出，不扩大原有保证。安装退出码、已安装 ASAR 一致性、原生启动、十次独立冷启动与卸载要求全部保留。

不采用简单增加固定超时、忽略失败、排除安全扫描或复制安装器模板。没有新增依赖或复制上游源码。CI 增加真实进程夹具，覆盖持续进展、停滞和总时限；实际安装日志必须证明旧时限之后是否仍在解压。如果仍停滞，继续据证据修复对应环节，不能把等待更久当作根因修复。
