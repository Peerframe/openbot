当前开发主线与验收状态见 [独立开发主线](DEVELOPMENT_TRACKS.zh-CN.md)。以下保留历史阶段记录。

## 目标

按依赖安全的顺序交付 OpenBot 下一阶段基础：先证明当前安全基线可靠，再建立可重复的
Windows、macOS、Linux 证据；随后交付原生工作主机与受保护的本机凭证，替换可复制的 Node
身份；然后加入可执行技能、受治理的记忆和分发；最后才开放真正的桌面控制。

Server 始终是员工身份、授权、路由、审批和审计的唯一权威。工作主机、Provider、模型、网页、
导入技能和消息始终视为不可信。办公室可视化继续作为延期的可选插件。

## 原生 Agent 循环——当前交付目标

当前用户目标是让 OpenBot 自己完成任务，而不只提供调度基础设施。在扩大可执行技能和桌面权限前，
先完成由 Server 管理的循环：

```text
频道任务 -> 领取 Run -> 模型规划/选择工具 -> Server 校验范围
                          ^                    |
                          +--- 有界观察结果 <- 只读工具
                          |
                     Bot 最终回复 / 明确失败
```

| ID | 状态 | 交付物 | 过线标准 |
| --- | --- | --- | --- |
| A0 | 已实现并通过本地验证 | 复用固定版本 Agent SDK 与现有 OpenAI/Anthropic 配置 | [调研](research/native-agent-loop.md)、精确版本与许可证、Owner 显式启用、不重放历史排队任务 |
| A1 | 已实现并通过本地验证 | 真正的模型—工具—观察迭代与当前频道只读工具 | 使用真实 SDK 的多步 HTTP 测试；工具范围、步数、时间、token 与输出上限；进度不含原始思维链或秘密 |
| A2 | 已实现并通过本地验证 | 持久 Run 生命周期与 Bot 回复 | 原子领取和完成、同频道串行、重启中断、配置变更/退出中止、PostgreSQL 测试 |
| A3 | 已实现；合并前须通过托管 CI | 通过共用 Desktop/Web 与 GitHub 交付 | 界面启用开关、中英文文档、完整检查和三端打包 CI；明确区分付费真实模型与隔离契约测试 |

首个循环服务于电脑配置为 `none` 的 Bot。已有 Worker 执行仍走原有路由；本目标不扩展桌面写入、
记忆检索、可执行技能或外部 Agent 委派。下方主机信任与分发阶段继续遵守原验收门槛。

## 为什么必须按这个顺序

```text
安全基线
   |
   v
三平台托管 CI --> 可重复的真实设备证据
   |                       |
   +-----------+-----------+
               v
      原生工作主机 + 系统密钥库
               |
               v
        Node 持有证明身份
               |
       +-------+-------+
       v               v
可安全执行的技能     受治理的记忆
       +-------+-------+
               v
       注册表与所有权转移
               |
               v
       真实输入与桌面接管
```

越靠后的阶段拥有越大的权限和影响范围。文档声明、模拟 fixture 或能力上报都不能替代下面的
证据门槛。

## 状态说明

- **已完成：**已经在所述证据等级实现并验证。
- **进行中：**当前正在执行的有界切片。
- **受阻：**需要明确的用户授权或外部基础设施。
- **已计划：**顺序已确定，但尚未开始。
- **延期：**明确不属于本目标。

## 每个切片的执行契约

每项非简单工作严格使用同一顺序：

1. 定义一条可观察的验收路径，以及权限、数据、副作用边界。
2. 搜索 GitHub、正式标准和平台第一方文档。
3. 比较维护状态、版本、测试、Issue、平台适配、安全边界和许可证，并固定审查的版本或提交。
4. 在改变行为或依赖之前，完成或新增 `docs/OPEN_SOURCE_REUSE.md` 条目和调研记录。
5. 实现最小、失败关闭、输入输出有界的纵向切片。
6. 按风险加入正常、负向、并发/生命周期和故障路径测试。
7. 更新英文原版文档，并同步面向用户的简体中文文档。
8. 运行针对性测试和 `npm run check`；涉及数据库、安装、安全或真实设备时再运行对应门槛。
9. 创建一个聚焦提交。完成一个切片只是检查点，不能用来跳过下一个依赖。

## 证据和支持声明规则

- 模拟 fixture 只能证明协议契约。
- 托管 CI runner 只能证明代码在该 runner 镜像上的构建与测试兼容。
- 密闭集成只能证明指定 Provider 和环境。
- 真实设备报告必须写明目标、OS 版本、架构、硬件、Provider 版本、场景版本、时间和可复现证据。
- `Supported` 和 `Certified` 必须有维护者审核的真实设备与安全证据。
- 凭证、权限、签名、扫描器、密钥库、时钟、存储或策略数据缺失时必须安全关闭，不能静默降低权限。
